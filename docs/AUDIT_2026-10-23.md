## Temuan berprioritas

### A01 — P1 bersyarat: dependency tooling rentan dan dev server terbuka ke jaringan

**Bukti:** `package-lock.json` memuat Vite 7.3.6 dan braces 3.0.3. Audit penuh melaporkan braces, chokidar, fast-glob, micromatch, tailwindcss, serta vite sebagai enam paket high. Ini bukan enam kerentanan independen: beberapa paket memperoleh severity dari satu dependency transitif. Vite juga mempunyai beberapa advisory berbeda.

`vite.config.js` mengatur `server.host: '0.0.0.0'` dan `cors: true`; `composer.json` menjalankan Vite dengan `--host`. Ini memperluas akses dev server jika firewall/jaringan mengizinkannya. Sebagian advisory Vite terkait Windows/editor dan dev-server access; eksploitabilitas bergantung pada konfigurasi dan reachability.

**Dampak:** prioritas tinggi jika dev server dapat diakses pihak tidak dipercaya. Audit produksi yang bersih tidak mencakup tooling ini. Tidak ada bukti dari audit ini bahwa bundle statis produksi terkena eksploit yang sama.

**Perbaikan:** naikkan Vite ke rilis patched yang kompatibel berdasarkan advisory tiap versi, audit kembali seluruh lockfile, dan batasi bind/CORS development secara default. Untuk braces, advisory saat diperiksa menyebut belum ada patch; evaluasi penggantian rantai dependency/tooling atau mitigasi input build. Jangan menjalankan `npm audit fix --force` tanpa memeriksa migrasi Tailwind.

**Gate CI:** `.github/workflows/ci.yml` hanya mewajibkan `npm audit --omit=dev`. Tambahkan pemeriksaan dev/build dengan kebijakan remediasi eksplisit agar alert ini terlihat; gate produksi tetap wajib sukses sesuai instruksi pengguna.

Sumber: [braces advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm), [Vite cross-origin advisory](https://github.com/advisories/GHSA-9jrq-w75r-8gcw). Severity dan seluruh rentang versi harus dibaca per advisory; severity agregat paket npm tidak sama dengan severity semua advisory Vite.

### A02 — P2, terbukti: bearer token akun nonaktif masih dapat membaca `/api/user`

**Lokasi:** `routes/api.php:9`, `bootstrap/app.php` registrasi `EnsureUserIsActive`, `app/Services/UserService.php:188–209`.

Middleware penonaktifan hanya ditambahkan ke grup `web`. `/api/user` memakai `auth:sanctum` dan `verified`, tetapi tidak memeriksa `is_active`. Penonaktifan staf tidak memanggil pencabutan token kecuali sekaligus mengganti email/password.

**Reproduksi:** buat user verified dengan `is_active=false`, terbitkan bearer token dalam test, GET `/api/user` dengan Authorization. Hasil **200**, bukan 403. Ini terbukti pada endpoint identitas tersebut; bukan bukti semua endpoint admin dapat dilewati karena endpoint admin lainnya memakai grup `web` dan role.

**Perbaikan:** middleware active-account pada semua akses authenticated termasuk Sanctum, mendukung request tanpa session; revoke personal tokens dan sessions ketika akun dinonaktifkan. Test ulang token yang diterbitkan sebelum penonaktifan melalui alur staf.

### A03 — P2, terbukti dari jalur request: token pelanggan dikirim lewat URL

**Lokasi:** `resources/js/Api/customerOrders.js:14–17`; `CustomerMenuController::orderStatus`.

Polling GET mengirim `customer_token` pada query string. Token ini adalah kredensial untuk membaca detail order dan membatalkan order pending. URL berpotensi tercatat pada access log/proxy/monitoring. Ini bukan klaim token sudah bocor; request API fetch juga tidak otomatis menjadi entri history navigasi biasa.

**Perbaikan:** kirim token melalui header khusus/Authorization atau body endpoint POST status; redact logging dan tentukan umur/rotasi token. `Cache-Control: no-store` yang sudah ada tidak menghilangkan query string dari log. [Rujukan OWASP](https://community.owasp.org/vulnerabilities/Information_exposure_through_query_strings_in_url).

### A04 — P2, terbukti: `payment.cash_enabled=false` tidak dipatuhi backend

**Lokasi:** `app/Services/PaymentService.php:20–57`, `SaveSettingsRequest::VALUE_RULES`.

Pengaturan cash tersedia dan valid, tetapi `processPayment()` hanya memeriksa enablement QRIS. Probe menyimpan `cash_enabled=false`, kemudian melakukan POS cash sale; hasil tetap **201** dan transaksi tercatat.

**Dampak:** setting metode pembayaran tidak menjadi aturan server. Kasir/API dapat menerima cash ketika owner menganggapnya dinonaktifkan.

**Perbaikan:** validasi metode aktif di jalur pembayaran baru maupun finalisasi payment pending, sinkronkan pilihan UI. Tetapkan perilaku jelas jika semua metode dimatikan.

### A05 — P2, terbukti: parameter periode laporan tidak menentukan rentang di backend

**Lokasi:** `app/Http/Requests/Report/ReportDateRangeRequest.php:14–22`; `ReportController::dateRange`.

`/api/reports?period=today` mengisi `start_date` dengan awal bulan. Probe menghasilkan `period=today`, `start_date=2026-10-01`, `end_date=2026-10-23`. Controller menghitung berdasarkan kedua tanggal tersebut. Halaman React biasanya mengirim tanggal lengkap, sehingga test custom range tetap hijau dan bug lebih terlihat pada URL langsung/API/integrasi.

**Perbaikan:** resolver rentang di backend untuk semua preset, gunakan input tanggal hanya untuk custom. Reuse resolver pada dashboard/pesanan/laporan agar label dan perhitungan tidak menyimpang.

### A06 — P2, terbukti: stok pecahan diterima lalu ditampilkan sebagai integer

**Lokasi:** `StoreProductRequest.php:35–36`, `Product.php:37–38`, migration products memakai decimal, sedangkan request inventory memakai integer.

Probe model dengan stock database `1.75` mengekspos `1`, minimum `0.50` mengekspos `0`. Form create menerima `numeric`; alur order dan inventory menggunakan jumlah integer. Audit trail `previous_stock` yang membaca cast dapat ikut kehilangan pecahan.

**Perbaikan:** putuskan satu kontrak. Jika semua stok per pcs, tolak pecahan di create/import dan rencanakan normalisasi data lama. Jika kabel/bahan boleh dijual pecahan, ubah cast, validasi order/inventory, kalkulasi, tampilan dan receipt secara konsisten. Jangan membulatkan data lama diam-diam.

### A07 — P2, risiko skala berdasarkan kode: pencarian server memindai seluruh kandidat

**Lokasi:** `app/Services/CatalogSearchService.php:243–283`.

Setiap pencarian membaca seluruh kandidat dalam chunk 250 beserta kategori/motor, menghitung skor di PHP, mengumpulkan semua ID matching, lalu membangun `WHERE IN` dan ekspresi `CASE` untuk sorting. Pagination akhir tidak membatasi biaya pencarian awal. Chunk membantu peak memory, tetapi bukan pembatas total CPU/query. Banyak kecocokan juga membuat SQL/binding besar.

**Perbaikan:** ukur pada katalog realistis, lakukan candidate prefilter terindeks sebelum fuzzy ranking, batasi jumlah kandidat, dan pertahankan contract vocabulary/mapping. Jangan menambah cache hasil pencarian tanpa strategi invalidasi stok/harga.

Belum ada EXPLAIN/p95 MySQL pada dataset produksi; ini temuan algoritme, bukan klaim latency server tertentu.

### A08 — P2, risiko skala: katalog publik mengirim semua produk dan menghitung seluruh histori penjualan

**Lokasi:** `CustomerMenuController.php:59–98`, `PosController.php:25–40`, `ProgressiveProducts.jsx`.

Katalog publik mengambil semua produk aktif beserta mapping motor dan mengagregasi order_items historis setiap halaman dibuka. POS juga memuat seluruh katalog. Pemangkasan kolom pada POS adalah peningkatan yang benar, tetapi ukuran payload tetap bertambah seiring katalog/mapping. Progressive rendering hanya membatasi komponen yang dipasang, bukan ukuran JSON yang diunduh atau query awal.

**Perbaikan:** endpoint search/pagination untuk pertumbuhan katalog, lazy detail/mapping yang tidak dibutuhkan layar awal, cache/agregat counter penjualan dengan invalidasi transaksi/retur. Pisahkan kebutuhan POS cepat dan katalog publik; jangan menghilangkan kemampuan pencarian berdasarkan motor.

### A09 — P2, risiko sumber daya: rentang laporan dan ekspor PDF belum dibatasi

**Lokasi:** `ReportDateRangeRequest.php:25–30`, `ReportService.php:118`, `ProductSheetExporter.php` cabang PDF.

Dashboard/pesanan memiliki batas sekitar 366 hari, laporan hanya memeriksa urutan tanggal. Ekspor laporan mengambil seluruh order + items. PDF produk mengambil seluruh produk dengan `get()` lalu render sinkron Dompdf. XLSX/CSV sudah memakai `lazy(200)`, jadi kekhawatiran all-memory tersebut tidak berlaku sama pada keduanya.

**Dampak:** laporan sejarah panjang atau PDF besar bisa menghabiskan worker/memory/timeout. Endpoint dibatasi owner, sehingga bukan anonymous DoS yang terbukti.

**Perbaikan:** batas tanggal dan jumlah baris, estimasi ukuran, queue export besar, download privat dengan cleanup. Uji PDF katalog besar dan multi-page pada PHP memory limit hosting sebenarnya.

### A10 — P2, terbukti dari validasi: pagination API administratif tidak punya maksimum

**Lokasi:** `ProductController.php:88`, `OrderController.php:141`, `PaymentController::index`, `InventoryController::index`.

`per_page` dibaca sebagai integer lalu langsung diteruskan. Produk web mempunyai whitelist, tetapi API tidak. Pada beberapa service nilai 0 juga beralih ke `get()` karena pemeriksaan truthy. Caller authenticated bisa meminta response sangat besar dan eager-load relasi.

**Perbaikan:** validasi terpusat `integer|min:1|max:100` atau whitelist; ekspor gunakan endpoint dan otorisasi tersendiri. Tambahkan test batas negatif/0/besar untuk setiap listing.

### A11 — P2, risiko concurrency: `sync_version` produk belum mencegah lost update

**Lokasi:** `ProductService.php:93–96`.

Update produk membaca model tanpa lock/version input, lalu menyimpan `sync_version = versi_terbaca + 1`. Dua edit paralel dapat menggunakan versi awal sama, menghasilkan versi akhir sama dan menimpa field yang sama. Jalur import sudah memeriksa fingerprint setelah lock, tetapi form edit biasa belum.

**Perbaikan:** optimistic compare-and-update menggunakan versi yang dikirim form dan response konflik 409, atau row lock dengan kebijakan konflik yang jelas. Increment atomic saja memperbaiki hitungan versi, tidak memberi tahu owner bahwa datanya ditimpa. Belum menjalankan stress test concurrency; interleaving diturunkan dari kode.

### A12 — P2, risiko operasional: POS memakai snapshot harga/stok yang tidak direkonsiliasi saat checkout

**Lokasi:** `resources/js/Pages/POS/Index.jsx:109–124, 189–195, 319–380, 400–414`; `Utils/posCart.js`.

Cart menyimpan harga/stok di localStorage. Total modal dihitung dari snapshot tersebut; server memakai harga database terkini. `handleNewOrder()` membersihkan cart tanpa refresh katalog. Setelah penjualan sendiri atau perubahan harga oleh admin lain, angka di kartu/cart dapat tertinggal. Server menjaga stok dan mencegah pembayaran tunai kurang, tetapi UX dapat berulang kali menawarkan barang habis. Pada konfirmasi QRIS manual, nominal yang dilihat kasir dapat berbeda dari tagihan server jika harga berubah.

**Perbaikan:** refresh stock setelah transaksi; validasi/quote harga terkini sebelum konfirmasi pembayaran, lalu pakai expected total/version pada transaksi agar perubahan harga meminta konfirmasi ulang. Ini bukan celah untuk memaksa server menerima harga dari browser.

### A13 — P2 aksesibilitas: dropdown periode custom belum menggantikan navigasi keyboard select

**Lokasi:** `resources/js/Components/PeriodSelectDropdown.jsx`.

Sudah ada `aria-expanded`, listbox dan Escape. Namun membuka dropdown tidak memindahkan fokus ke pilihan; belum ada ArrowUp/Down/Home/End, active option dan pengembalian fokus. Pada mobile popover fixed juga tidak memiliki perilaku modal/focus trap sehingga keyboard dapat berjalan ke kontrol di belakangnya.

**Perbaikan:** gunakan Headless UI Listbox/Popover yang sesuai pola interaksi, atau implementasikan pola listbox lengkap. Uji keyboard dan screen reader, tidak cukup hanya menambahkan role ARIA. Status ini berdasarkan kode, belum audit pembaca layar pada perangkat nyata.

### A14 — P3, maintainability dan konsistensi visual

- `resources/views/app.blade.php` berisi **1.703 baris** skeleton/layout yang menduplikasi struktur React. Ini template shell awal, bukan React SSR. Perubahan filter/card harus diulang di dua tempat; risiko flash/layout shift kembali muncul. Pecah partial shell dan tetapkan ukuran/contract bersama.
- Halaman Product ~97 KB source, Motorcycle ~94 KB, POS ~69 KB, Order ~61 KB. Ukuran source bukan ukuran download. Ekstrak domain/form/flow untuk mempermudah review; jangan refactor besar tanpa regression checks.
- Hanya **19 dari 117 file PHP pada app/** memiliki `declare(strict_types=1)`, berlawanan dengan AGENTS.md. Pint default tidak memaksakan aturan ini. Terapkan bertahap bersama pengetatan tipe dan static analysis; ini bukan bukti 98 vulnerability.
- `PeriodSelectDropdown.jsx:105` memakai `bg-slate-950/40 backdrop-blur-xs`; beberapa modal baru juga memakai opacity. `Report/Index.jsx:268` masih `dark:text-blue-300`. Itu menyimpang dari palet/aturan solid dalam AGENTS.md. Jika desain overlay transparan memang sekarang dikehendaki, dokumentasikan pengecualiannya secara eksplisit.
- Dokumentasi menyebut role manager; RoleSeeder dan StoreUserRequest hanya mendukung owner/cashier. Selaraskan dokumentasi dan kebutuhan bisnis sebelum menambahkan role baru.

## Hal yang sudah benar dan telah diperiksa

- Harga order dihitung dari database; input harga browser tidak dipercaya.
- Order, payment, return dan stock mutation memakai transaction serta row lock. Nomor dokumen menggunakan sequence yang dikunci. Idempotency checkout memasukkan channel/actor/payload; test retry tidak hanya bergantung pada tombol disabled.
- Retur membatasi quantity sisa, refund proporsional dan sisa pembulatan, dengan log stok melalui InventoryService. Probe retur penuh: net revenue 0, gross tax 1.000 dan sold quantity 1. UI secara eksplisit menandai breakdown kategori sebagai sebelum retur; itu tidak dilaporkan sebagai double-count bug. Label top-selling dapat dibuat lebih jelas jika ingin membedakan gross vs net units.
- Controller sensitif mempunyai server authorization; penyembunyian tombol bukan satu-satunya kontrol. Login memakai throttle, session regeneration, pemeriksaan akun active dan invitation.
- Upload membatasi format/ukuran/dimensi, menolak SVG lewat whitelist format, re-encode WebP dan strip metadata. Import mempunyai batas ZIP/XML/rows/cells, preview ownership, fingerprint dan commit receipt. CSV memakai perlindungan formula untuk prefix umum dan XLSX memakai StringCell.
- CSP nonce, security headers, cookie HttpOnly/SameSite/secure configuration tersedia. Tidak menemukan `dangerouslySetInnerHTML`/`document.write` pada scan sumber JS yang diperiksa. Ini tidak menggantikan pengujian XSS dinamis.
- Service worker tidak meng-cache halaman/API privat. PWA bersifat online-first, bukan sistem offline transaksi.
- Deploy produksi memeriksa CI sukses untuk SHA yang sama. Script backup memakai file privat, password tidak dimasukkan ke argv, dan health check juga mengetes DB. Ada prosedur manual rollback pada `docs/GITHUB_WORKFLOW.md`.

## Deployment, operasi, dan batas bukti keamanan

Screenshot pengguna menunjukkan beberapa run PR #114 gagal lalu run berikutnya dan merge/deploy sukses. Riwayat merah tidak berarti deploy terakhir gagal. Alasan tiap run merah tidak diketahui hanya dari screenshot dan tidak ditebak.

CI sukses saat ini memverifikasi dependency produksi npm; itu konsisten dengan alert build/dev yang tetap ada. Rebuild staging/production memakai npm bawaan Node 22 sedangkan CI memasang npm 11.19.0. Samakan toolchain agar hasil audit/install lebih mudah direproduksi. Ini risiko reproducibility; bukan klaim deployment terakhir rusak.

Backup otomatis per deploy dan rollback manual sudah ada. **Belum ada bukti restore drill dan backup off-host berhasil** dari sesi ini. Tidak menjalankan deployment, rollback, email nyata, perubahan user produksi, atau load test terhadap situs publik. Konfigurasi Nginx/Apache/TLS/firewall, secret GitHub, branch protection, cron/worker server, retention disk dan error monitoring belum diverifikasi. Tidak membaca/menyalin nilai rahasia .env ke laporan. Scan file terlacak menemukan .env.example, bukan bukti ada credential aktif yang committed; history Git seluruh masa belum diaudit secret secara menyeluruh.

1. Tutup eksposur dev server bila dapat dijangkau jaringan tidak dipercaya; remediasi advisory Vite dan strategi braces, lalu audit lockfile penuh lagi.

6. Ukur dataset staging realistis sebelum mengubah algoritme pencarian/katalog; prioritaskan query/payload yang mahal, pertahankan behavior pencarian motor.
7. Uji keyboard/date dropdown, responsive 360/390/768/1024/1440, PDF panjang dan alur kasir di browser; lanjutkan restore drill di staging.

Hasil audit ini menyediakan daftar kerja terukur. Perbaikan implementasi belum dilakukan pada sesi audit ini.
